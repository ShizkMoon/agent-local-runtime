# code-review

两轴审查：**标准**（这个仓自己的规矩：命名/分层/错误处理/测试习惯）与**规格**（这次改动要求的事做到没有、有没有多做）。两轴分开走，最后合并成一份带位置的清单。

## 适用

- 用：提交前自审、审分支/PR、reviewer 节点验收、重构后核对行为未变。
- 不用：任务本身就是"实现"（先实现再自审）；只想知道"能不能跑"（那是 test-first / 直接跑）。

## 步骤

1. **定基线**：拿到改动范围（`git diff <base>..HEAD`、某次 commit、或 `git status` 的未提交改动）。基线不清就先问，别猜。
2. **读规格**：找到这次改动的原始要求（issue/spec/PR 描述）。找不到就写"规格缺失"，按"标准轴"单独出结论。
3. **标准轴**：逐条比对仓里的既有约定——同类文件怎么写、错误怎么抛、日志怎么打、测试放哪。**引用一条既有代码作为依据**。
4. **规格轴**：逐条核 `accept` 项：做到 / 没做到 / 超范围。超范围单列，不算 bug 但要报。
5. **定性分级**：`blocker`（会错/会丢数据/会泄露）、`major`（行为偏差、漏测）、`minor`（可读性、重复）、`nit`（纯风格）。级别决定要不要在上线前修。
6. **出清单**：每条 `file:line` + 一句话问题 + 具体后果 + 建议改法。不夹带"整体不错"这类无信息量的话。

## 验收

- 每条 finding 都有 `file:line`，都能被别人复现（点开那一行就能看到）。
- `blocker` 必须写清"什么输入/状态 → 什么错误结果"，写不出就不是 blocker。
- 两轴都有结论；某一轴没有发现，要显式写"标准轴：未发现问题"，不能省略。
- 报告里不出现没有位置的"建议重构"。

## 反例

- 只看 diff 不看上下文：一个删掉的守卫，在 diff 里像清理，在文件里是漏洞。
- 把个人风格当 blocker，把真 bug 降成 nit。
- 没读规格就开审，把"没做需求"漏掉，只挑语法。
- 顺手改代码：审查和修改混在一起，reviewer 就失去了独立视角。
- finding 写成"这里可能有问题"，没有场景、没有位置，等于没写。

# release-notes

发版说明写给**使用者**看，不是写给 git 看。每条都要能回答"我这版会感觉到什么变化"。

## 适用

- 用：发 tag 前整理变更、给内部/外部写发布公告、补 CHANGELOG。
- 不用：日常提交信息（那是 commit 的事）；还没合并完就写（区间会漂）。

## 步骤

1. **定区间**：`git log --oneline <上个 tag>..HEAD`。没有 tag 就用上次发布 commit；区间写进说明开头。
2. **拉全量**：带 `--no-merges` 看提交，必要时 `git log -p` 看关键改动。**只看标题会漏掉真实的破坏性变更**。
3. **分类**：新增 / 修复 / 性能 / 文档 / 内部（构建、依赖、重构）。内部项默认合并成一行或省略。
4. **写人话**：把"做了什么实现"翻成"用户能做什么/不再会遇到什么"。每条末尾附 commit 短 hash 或 PR 号。
5. **单列破坏性变更**：接口、配置键、数据格式、CLI 参数、默认值的改动。**没有也要写"无"**。
6. **校验**：随机抽 3 条回查代码，确认描述与实现一致；检查有没有把未合并分支写进去。

## 验收

- 每条变更带 hash 或 PR 号，能点回去。
- 破坏性变更段落存在（哪怕内容是"无"），且每条都写了迁移动作。
- 不出现"优化代码""修复一些问题"这类空话。
- 区间与 tag 对得上：说明开头写的起点终点，能和 `git log` 复现。

## 反例

- 直接把 `git log` 原文粘贴，用户读到一堆 `fix: typo`。
- 把内部重构写成用户可见的新功能，读者白高兴。
- 漏掉破坏性变更：改了默认端口/配置键，升级即炸。
- 按提交数量而不是影响面排序，重要的修复埋在最后。

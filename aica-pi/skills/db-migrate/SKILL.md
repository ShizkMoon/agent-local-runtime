# db-migrate

迁移的危险不在写错 SQL，而在**没有退路**和**锁表**。顺序比内容重要：先想好怎么退，再动手。

## 适用

- 用：加/改/删列、加索引、改约束、数据回填、拆表合表。
- 不用：临时查数改数（走单独的、有审计的脚本）；纯 seed 数据（另走 fixture）。

## 步骤

1. **确认退路**：先确认备份可用（最近一次全量 + 增量），并写下**回滚判定条件**（什么现象就回滚）。
2. **写 forward**：一条迁移只做一件事；**幂等**（`IF NOT EXISTS` / 先查后建），可重复执行不报错。
3. **写 rollback**：与 forward 一一对应的 down 脚本。写不出来，说明这步不可逆——先停，改方案或加双写过渡。
4. **副本演练**：在数据副本或本地容器上跑 forward → 校验 → 跑 rollback → 再校验，确认能回到基线。
5. **估锁与耗时**：大表加索引/改列要估行数与锁窗口；超时的改成分批 + 可中断（`LIMIT` 循环、记录游标）。
6. **分步上线**：先加兼容结构（新列可空）→ 双写/回填 → 切读 → 观察 → 最后删旧结构。**删永远放最后一个版本**。

## 验收

- forward 与 rollback 都实际执行过，rollback 后 schema 与数据回到基线（对比 diff 为空）。
- 迁移可重复执行：连跑两次不报错、不产生重复数据。
- 回填有分批与进度记录，中途中断可续跑。
- 有"回滚判定条件"和"观察多久再删旧结构"的明确数字。

## 反例

- 只写 forward，出事只能手工改库。
- 一步 `rename` 或 `drop`：老代码还在读旧名，滚动发布期间必炸。
- 在迁移里跑全表 `UPDATE` 或长事务，锁住整张表。
- 没在副本上跑过就直接上生产。
- 回填脚本没有游标，失败重跑从头再来。
